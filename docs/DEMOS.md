# Demos

Every visible behaviour of agent-neuron has a demo here, so the ideas can be
watched and argued with, not just read. Keep this table current: a feature
that adds or changes visible behaviour adds or updates its demo and its row.

| Demo | Command | What it shows | Status | Open questions it informs |
|---|---|---|---|---|
| First example | `echo approve \| npm run example` | A shell script, a local HTTP API and a human on stdin as three neurons in one network; a waiting `send` between them. | working | Who decides where an answer goes next; what a failed neuron means for the run. |
| Typing | `npm run demo:typing` | A search box emits the query one letter at a time without waiting (`emit`). Three neurons with different latencies each decide in their own adapter whether to act. A newer prefix replaces the older one: stale work is aborted and printed as dropped. Answers carry no prefix: the demo keeps a map of what it emitted and finds each answer's prefix through `replyTo`. Made-up catalogue. | working | What a passive channel is, as opposed to an active one; whether the wrapper or the network should decide to act on an input; which answers count as useful. |
| Typing, tracks in Rust | `npm run demo:rust` | "Wrap anything" across languages: the typing demo with its tracks neuron replaced by a small Rust program (`rust/catalogue`, std only) run through the shell adapter. Same rule and catalogue as the JavaScript neuron, so the answers agree; the neuron id `tracks (rust)` shows where they come from, and stale work is still aborted and printed as dropped. Needs a Rust toolchain. | working | Whether the wrapper really is language-neutral; what crossing a process boundary costs (a spawn per signal); where a composed neuron's inner network could run in another language. |
| Composed neuron | `npm run demo:composed` | The first working composed neuron: a Rust program `music` (`rust/music`, std only) holds its own small inner network of tracks, artist and lyrics neurons, and to the TypeScript network it is one neuron through the shell adapter. The search box sends each keystroke to `music` alone; answers and stale drops print as in the other demos. The outer network sees a signal in and an answer out, with no inner ids. Then one standalone `music --inspect` run prints the inner trace (signal ids, replyTo, one trace id), labelled as the inside view. Learning is not built: each call is its own process and nothing is shared. Needs a Rust toolchain. | working | Composition; tracing across the boundary (traceable from inside only); what each use learning on its own will need (state that outlives a process). |
| Suggest (threshold) | `npm run demo:suggest` | The typing demo plus a `suggest` neuron with `threshold: 2`: the answers of tracks, artist and lyrics are forwarded to it with `{ cause }`. It holds one answer per keystroke and acts only when a second neuron answers the same keystroke; the demo prints each run with the senders that agreed, the held answers dropped as "stopped waiting: newer answer" (replaced by a newer forward) or "gave up waiting" (expired after `within`), and "suggest ran N times for M keystrokes" with a closing note on why only the last keystroke can agree. `demo:typing` is unchanged. | working | Whether agreement should weigh senders differently (strength, next); what a neuron does with the rest of a trace after it has acted. |
| Loop cut | `npm run demo:loop` | Two neurons, ping and pong, that take turns forever: an `onSignal` handler has each answerer pass its answer on to whoever it answered, with `{ cause }`, so both adapters run in turn ("start > pong > ping > pong"). Each has `maxHops: 5`; the demo prints every hop and the `onDrop(..., 'hops')` that ends the loop. Separate from the first example to keep that one a plain three-adapter tour. | working | Whether a limit per neuron is enough, or loops also need a budget per trace; who should forward answers (the caller today). |
| Alert storm | `npm run demo:alerts` | Use case 2 ([USE-CASES.md](USE-CASES.md)): 40 invented alerts for five invented services in about six seconds. An `alerts` source emits each with `replaces` keyed by service. Three cheap detectors decide for themselves: `logs` and `deploys` are POSIX sh scripts wrapped by `ShellAdapter`, `metrics` is JavaScript. Their flags are forwarded with `{ cause }` to `hypothesis` (`threshold: 2`, a fixed 500 ms standing in for a model), which runs only when two distinct detectors flag the same alert; each run counts as one expensive call. Its result goes on to `diagnosis`, a composed neuron: an adapter with its own inner network (topology lookup, read-only deploy check) that is never added to the outer one, so the outer network only ever sees one verdict. Prints one line per finished call and a summary (calls started instead of 40, how many were cut short as stale and still spent, waiting flags replaced, final diagnosis); the numbers are the same on an idle machine, and a test asserts invariants only (`test/alerts.test.ts`). Timing is chosen so ordering is stable: alerts for one service come 150 ms apart or 900+ ms apart, and a shell detector must finish within about 150 ms. | working | Whether a threshold over a trace is the right unit (a burst of alerts is several traces); whether a call cut short as stale still counts as spent; what stops the network re-diagnosing a cause it already knows (all diagnoses agree); what a composed neuron built in JavaScript costs compared with one in Rust. |
| Network view | `npm run view` | A local page (`examples/view/`, no framework, no outside requests) that draws a demo's network live while it runs: pick alerts, typing or suggest and press Run. Nodes and edges appear as the first signal touches them; markers travel along edges (a circle for a signal, a diamond for an answer), each node shows its last event in words (answer, quiet, stale, gave up, hops, acting, error) with counts of what it answered and dropped, edges thicken with traffic, quiet answers fold into one log line, a threshold neuron shows how many inputs it is "waiting" on, and a log carries every event as text. A composed neuron is one node: in the alert storm `diagnosis` appears and its inner neurons never do. The demos themselves run unchanged in the server process; the page only listens. | working | What an observer can and cannot see of a network from its traffic alone; what the graph should show once connections have a strength. |
| Trace recorder | `npm run record -- alerts` | Not a demo to watch: it runs the alerts, typing or suggest demo and writes what its network did (every signal, answer, quiet answer, drop and error, with times) to `traces/<demo>.json`, with the neurons declared up front and the demo's own summary numbers. The alert storm is recorded three times, with `hypothesis` acting at 1, 2 and 3 detectors. A small replay module folds a trace to any moment; the network view counts with the same module. Format in [TRACE.md](TRACE.md). | working | What a replayable record of a run needs to carry; whether the numbers survive a different machine (they do not: timing). |
| Network file | `npm run demo:network` | The alert storm again, with no neuron or routing code: the engine (`src/engine/`) reads `spec/examples/alerts.network.json`, injects the 40 timed alerts of `alerts.inputs.jsonl`, runs the detectors as processes, forwards along links, holds `hypothesis` until two detectors agree, cuts stale calls, and runs `diagnosis` as a composed neuron. Prints a summary read from its own trace (flags, calls instead of 40, cut, replaced, expired, the last diagnosis, and that no inner id appears). `npm run demo:network -- spec/examples/alerts-python.network.json` swaps `hypothesis` for a Python program, and `-- spec/examples/alerts-python-serve.network.json` for a long-lived (level 1) Python program that handles `cancel`: the same invariants, the same event counts apart from the `term` notes. Per signal, on one machine, a level 0 Python neuron costs a process start (median 19.7 ms) and a level 1 one a pipe round trip (median 0.04 ms), against the storm's detector budget of about 150 ms (SPEC Appendix C; informative, not asserted). The numbers match `demo:alerts`'s on an idle machine; a test asserts invariants only (`test/engine.test.ts`). | working | Whether a network file says enough (the only caller-side piece left is the producer's keys, [decision 0002](decisions/0002-alert-storm-mapping.md)); what any other engine must match. |
| Conformance | `npm run engine -- conform spec/fixtures` | Not a demo to watch: the engine run on 158 fixtures (148 run, 10 pending) (a network file, scripted inputs, scripted neuron replies on a virtual clock, exact expected events). Prints pass, fail or pending per fixture and exits non-zero on a failure; the same command any other engine must offer ([CONFORMANCE.md](CONFORMANCE.md)). | working | What an engine must do exactly, and what the specification still leaves open (decision 0004). |
| Real-time search page | not built yet | The same music search in a browser, with the concerts and links neurons, results a person can click. Issue #11. | planned | Whether a click is a signal that strengthens a connection; chains inside the network (concerts listens to artist). |
