# Decision record 0013: peer-to-peer (2026-11-09)

**Status: decided (Kevin, 2026-11-09)** — the shape and the placement rule below
are accepted. **P0 is built and gated** (2026-11-09): `run --peers <file>` and
`neuron-engine peer`, `src/peers.rs` with 6 tests in `tests/peers.rs`, `cargo
test` 98, `conform spec/fixtures` 224/0/0 on five consecutive identical runs and
`conform py/probes` 10/0/0 unchanged. P1-P4 are planned, not started. The plan of
record, with the seams, the breakages and the per-step gates, is
[docs/P2P.md](../P2P.md). Nothing in this record changes the SPEC: P0 and P1 add
no contract, and the contract pass (P5) is a separate commit this record's

## The problem

The engine is one process with one clock and one event list (SPEC 6.2), and the
protocol says a boundary between parties is an `http` neuron to that party's own
engine (2.6), which keeps its inside and its accounting to itself. The family's
pitch is the opposite of a controller: no scheduler, the graph is the referee —
and the ground (0012) is shared state by construction. The Flow question of the
whitepaper ("one program, separate local processes, or across machines?") was
answered as "across machines via MCP, the run record as the shared state"
(docs/MULTIPLAYER.md). That answer keeps the rules inside one engine. This record
takes the next step: the rules themselves span hosts.

## The decision

1. **The destination is B: partitioned referees.** Every peer runs the slice of
   the graph it hosts, holds that slice's full engine state (slots, held inputs,
   threshold groups, budget, ground view), and only signals cross a peer edge.
   Each neuron lives on exactly one peer, so a hold, a threshold group and a
   `serve` slot stay local facts. A composed instance is atomic: it is planted
   wholly on one peer, because sealing and its shared inner processes make it the
   natural unit of placement.
2. **It is built through A: one referee dispatching calls to worker hosts.** A
   keeps SPEC 6.2 exactly — one clock, one event list, one trace — so the same
   conformance suites and the same trace reader stay the regression. The seam is
   the engine's own: every external executor reports into one queue stamped at
   read time (`host.rs:66` `Ev`, `engine.rs:1173` `host_step`), and `Engine::emit`
   (`engine.rs:686`) is the single reporting point. A remote call is a new `Ev`
   variant and a thread, the shape `http.rs:85` and the desk already use.
3. **Placement lives in a side file passed at run (`--peers`), not in the network
   file.** It is the `--grants` pattern of decision 0010: deployment is the
   deployer's, the network file is the house rules. This also keeps SPEC 2.8's
   field budget whole — a placement field would say neither how neurons connect
   nor how one decides, and 2.8 has no slot for a third class. A SPEC field is
   revisited only if P2 proves a shape worth standardising.
4. **The wire is hand-rolled, std-only, like the rest of the crate.** Newline-
   delimited JSON over TCP, versioned `v: 1` like the level 1 protocol, messages
   `hello` / `call` / `answer` / `quiet` / `error` / `cancel` / `cut` / `deposit` /
   `settled`, caps matching the local ones (1 MiB payload and line, 256-byte
   keys). `Cargo.toml` keeps zero dependencies: no TLS, no async, no crypto crate.
   `hello` carries a digest of the network tree (FNV-1a over the file text: an
   agreement check, not authentication) and the peers refuse a mismatch.
5. **A multi-peer trace is segments plus a merge rule.** Ids stay opaque strings
   (TRACE.md) and the header names the scheme (`trace.rs:24` `run-numbered`); a
   `peer-numbered` scheme is an addition a v1 reader already tolerates. `emit`
   stamps the origin and the merge orders by `(stamp, peer)`. A multi-peer trace
   is deterministic and *not* equal to any single-engine order; the single-host
   trace is unchanged, byte for byte.
6. **Fixtures never open sockets.** A peer is scripted on the virtual host like a
   program and a person are: the script answers `call` messages and scripts
   `cut`/`settled`. That is how B's non-local behaviour gets pinned, and why P2
   precedes P5.

## Why A is not a detour

The work A needs is the work B needs, minus the order problem. P0 proves the
transport, the call lifecycle across a socket (cancel, timeout, crash, restart,
`effect` → `unknown` on a dead peer, budget reserve/commit) and the trace
identity. P2 then turns the same messages into signal routing and P3 into the
trail. Skipping A would mean rewriting the call lifecycle against a distributed
clock at the same time as inventing the clock.

## Not decided here

- **The clock rule.** A hybrid logical clock (physical ms + counter) per peer and
  a deterministic `(stamp, peer)` merge is the recommendation; it is accepted in
  principle at P2, where a merged trace first exists to read.
- **Budgets.** Declared per-peer shares at the plant first (no coordination, a
  peer can starve while another sits on units), an owner per trace later. The
  trace's owner is not a controller of the network; it is one arbiter per trace.
- **Security posture.** A pre-shared secret per peer with a counter and a MAC per
  line (hand-rolled SHA-256/HMAC), inside a trusted network; or an explicit trust
  mode that says so on stderr. No TLS in a std-only crate.
- **Quiescence.** Distributed termination detection (Dijkstra–Scholten over the
  traffic, or a heartbeat and view exchange) — issue #30 item 4, now the keystone
  under B as it already is under carry-over.
- **Remote humans.** The desk stays on `127.0.0.1` in v1 (0008's rule list
  unchanged); answering from another machine is its own decision.
- **A SPEC field for placement** — see 3 above.
